# Domain glossary

## Task definition

The immutable description of one test run: the target application, shared model
connections, and the test items to execute. Runtime progress and results are not
part of the task definition.

## Test item

One independently configured part of a task. A test item is either a baseline
dataset test or a risk attack test, and its identifier is unique within a task.

## Baseline dataset test

A test that executes an imported dataset according to its selected cases and
evaluation rules. It does not automatically start a risk attack.

## Risk attack test

A test aimed at one risk category. Its initial cases may be sampled from one or
more datasets, generated by the shared attacker model, or obtained from both.

## Test case

One concrete test input that can be executed and evaluated independently. A
test case records its own identifier, its owning task and test item, its
initial prompt, and whether it came from a versioned dataset entry or from
model generation. Risk, evaluation, and round-limit configuration remain on
the referenced test item rather than being duplicated on the case.

One single-round case produces one step. A multi-round case produces multiple
steps in the same target conversation.

## Case source

The provenance of a test case. A dataset source identifies both the exact
dataset version and the source case identifier. A generated source records
that the case was produced by the task-level attacker model.

## Attack strategy pool

The strategies available to the attacker for a risk attack. The pool is a set of
choices, not an instruction to execute every strategy or strategy combination.

## Attack process

The independent sequence started from one initial case. Each process may run up
to the risk test item's configured maximum number of rounds.

## Step context

The immutable, attacker-facing input assembled by TaskRunner for one round of a
risk attack. It identifies the task, test item, test case, current step, current
round, and maximum rounds. It also contains a safe target profile, a resolved
risk objective, the fully resolved strategies available for this round, and
the complete evaluated history of earlier rounds in the same test case.

Step context is not used for baseline dataset execution. It does not expose the
target model name, endpoint, credentials, target-session identifier, evaluator
rules, runtime status, or timestamps.

## Target profile

The target name and business description that may safely be exposed to the
attacker. Connection details and credentials remain outside the attacker-facing
context.

## Risk objective

The resolved risk identifier, name, description, and concrete objective for the
current attack. Unlike the optional objective override in a risk test item, the
objective in step context is always present.

## Available strategy

A fully resolved attack strategy that the attacker may choose for the current
round. It contains a strategy identifier, name, description, and guidance. The
attacker may select a different available strategy in each round.

## Step history entry

One fully executed and evaluated earlier round in the current test case. It
contains the prior step identifier and round number, the selected strategy, the
attack prompt, the normalized target response, and attacker-visible evaluation
feedback. History is ordered, contiguous, and isolated to one test case.

## Evaluation feedback

The evaluator information safe to return to the attacker: whether the attack
succeeded, an optional normalized score from 0.0 to 1.0, and a reason. Internal
evaluation rules and evaluator prompts are not part of this feedback.

## Attack decision

The single final output produced by the attacker for one step context. It
repeats the task, test-item, case, step, and round identifiers for traceability,
then records the selected strategy, the normalized text prompt to send to the
target, and a required decision summary of at most 200 characters.

The decision contains no provider-specific request body, target-session
identifier, stop instruction, termination reason, runtime status, timestamp,
or full chain of thought. TaskRunner verifies that its identifiers match the
input step context and that its selected strategy was available for that step.
TaskRunner or the persistence layer also guarantees that one step identifier
has at most one final attack decision.

## Task context

The task-level snapshot maintained by TaskRunner for one task run. It records
the overall state, current execution position, progress of every test item, and
the task-level termination reason. Detailed steps, decisions, responses, and
evaluations are separate records.

## Test item progress

The task-level progress summary for one test item. It records how many cases
exist, how many have finished processing, and how many ended with technical
errors; it does not contain individual case outcomes.
